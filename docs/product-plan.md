# 丸宠APP · 功能拆解与开发路线

## 1. 产品定位与决策状态

已确认：名称「丸宠APP」；iOS 为目标平台；必须有后端；以《旅行青蛙》式轻养成、准备行囊、离线旅行、归来收集的节奏为参考；主角是多物种 AI 宠物，不局限青蛙；新建独立项目与 GitHub 仓库。

原创边界：借鉴品类循环与安静陪伴感，重新设计角色、场景构图、图标、文案与界面，不描摹原作截图，不提取其素材。参考不是授权。

首批视觉已于 2026-10-17 确认为三花猫、清透日系绘本和第一张“窗边小屋”方向，后续明确继续 2D 水彩动画；美术资源不替换服务端测试配置。当前已完成互动家园预览，以及服务端 start/claim 测试闭环，见 [旅行验收记录](travel-backend.md)。待确认：正式世界观、猫咪名字、AI 实施优先级与供应商、正式账号恢复方案、生产云区域、预算、付费/广告。以下未单独确认的数量与方案仍为开发建议。

## 2. 玩家核心循环

回家看宠物 → 获得少量日常资源 → 商店准备食物与用品 → 放入行囊并保存 → 服务器根据宠物性格与配置决定何时/前往何处 → 宠物自主出发 → 玩家离开或查看旅途状态 → 宠物带回纪念品与明信片 → 领取奖励、收藏、准备下一次旅程。

宠物自主出发是目标体验，玩家准备行囊而非每次强制命令出发。服务器规则引擎结合性格、有效行囊与版本化配置选择出发窗口和目的地；后台调度或读请求惰性推进都要幂等。

AI 增加陪伴感和叙事个性，但不能决定余额、掉落概率、旅行时长或道具所有权。AI 可叙述自主选择，实际旅行与经济状态由规则引擎验证。

## 3. 功能矩阵

| 模块 | 首个 MVP 建议 | 后续版本 | 验收标准 |
|---|---|---|---|
| 账号与存档 | 会话、唯一玩家、跨启动恢复；持久账号绑定/恢复方案待确认 | 多设备会话管理 | 已绑定可恢复身份登录后恢复服务端状态；未绑定匿名账号不承诺清缓存/重装恢复 |
| 宠物身份 | 数据驱动物种、昵称、性格标签、状态 | 多宠物切换、关系成长 | 物种切换不写死在 UI，昵称过滤可回退 |
| 家园 | 庭院/室内两层场景、宠物待机与离家态 | 装修、天气与来访 | 进入场景始终匹配服务端快照 |
| 日常资源 | 一类基础资源、领取规则 | 季节资源、日常事件 | 时间依据服务器；重复领取不增发 |
| 背包商店 | 6 个示例道具、数量与价格配置 | 稀有道具、皮肤 | 买入与扣款同一事务，不出现负库存 |
| 行囊 | 建议 3 个道具位、明确消耗提示 | 多套预设、进阶道具 | 不足/过期配置时拒绝出发且不扣款 |
| 旅行 | 1 条短旅程、1 个宠物同时最多 1 次 | 区域、路线、事件池 | 断网重连、杀进程、重复出发均无重开或多扣 |
| 归来结算 | 服务器预定奖励、幂等领取 | 稀有事件与好友合照 | 并发重放 100 次领取只产生一笔奖励 |
| 明信片与图鉴 | 3 张原创样例、收藏详情 | 稀有度、搜索、主题册 | 图鉴与奖励账本保持一致 |
| AI 陪伴 | 聊天/记忆与旅行日记/明信片均包含；分阶段实现，对话/记忆已进入本地验收 | 更丰富的长程陪伴与叙事 | AI 失败不阻塞旅行或奖励；消息重试去重，记忆可查看、确认和删除 |
| 通知与设置 | 音效/动效、隐私入口 | 经同意的归来推送 | 拒绝通知权限仍可完整玩主循环 |

## 4. AI 功能范围（两类均已确认）

A. 聊天与记忆：宠物按物种/性格回应；短期上下文与用户可见、可删除的长期记忆分开。聊天与记忆保留到用户删除；敏感内容须明确要求记忆，凭据始终排除。用户年龄范围与正式上线策略仍需独立明确。

B. 旅行日记与明信片文案：用已结算的目的地、事件和纪念品生成短叙事，模板文案兜底。当前美术使用固定原创资源；2026-10-23 已确认并实现 Seedream 生图、图片聊天及 10% 新图/90% 共享图库复用，本地验证范围详见 [图片功能](pet-images.md)。生成图片不得阻塞奖励领取。

C. 已确认两者都有：先分开验收，再组合。统一宠物人格、主人可管理的记忆及旅行经历，聊天可以引用真实已发生的旅程；私人聊天与敏感记忆不得自动出现在可分享的明信片中。分享前提供预览，默认仅使用已批准展示的旅行事实。生成费用、延迟、内容审核与用户预期都需要预算与质量门槛。

2026-10-23 已确认并实施 TokenHub Haiku + Codex SDK + 自托管 mem0，对话/记忆优先于旅行叙事；详见 [宠物对话需求及验收](pet-chat.md)。AI 仅在服务端调用、受预算限额与速率限制；文本视为不可信展示内容；不能执行数据库操作、触发奖励、向外部发消息或修改宠物资产。宠物人格与叙事风格配置版本化，禁止把真实用户记忆放进公共资源包。声明虚拟 AI 身份，避免引导用户依赖或误解为真人。

聊天与记忆界面必须可独立验收：发送失败/重试/重复提交不生成多条用户消息；用户可查看自动提炼的记忆条目及来源，纠正、删除或全部清空；删除后不再供后续生成引用，并说明历史对话是否另行保留。聊天与主人记忆默认私有，可分享明信片默认只取旅行事实，分享前允许审阅，不能自动摘录私聊。

## 5. 第一条垂直切片：验收脚本

1. 建立测试玩家与初始背包，客户端读取 revision 与 serverNow。
2. 为验证闭环，调试/垂直切片可直接提交带唯一幂等键的 start；正式 UI 保存行囊后由服务器自主触发出发。选择道具并提交 start；服务端验证与扣除，返回 tripId、returnAt。
3. 连点、超时重试、双设备并发后，只有一个有效旅程和一次扣除。
4. 客户端改时间 ±7 天，旅程归来时间与奖励都不变。
5. 到期后服务端允许 claim；过早领取返回确定错误，不产生账本。
6. 奖励、背包、收藏与旅程状态原子提交；同键重试返回原结果，不同键重复领取也不增发。
7. 杀进程或断网后重进，从服务器恢复。过期缓存只能查看，不能离线消费或领取。
8. AI（实现后）超时/拒绝/输出异常时，展示模板文案，经济闭环仍完成。

## 6. 实施阶段与出口条件

- P0 准备：确认具体宠物、AI 实施顺序、供应商和仓库开发流程，锁定设计边界；交付本计划、工程骨架、工具研究。
- P1 后端闭环：认证、数据库 schema/迁移、配置、start/claim、账本、数据库集成与并发测试通过。
- P2 可玩界面：家园—行囊—旅行—归来—收藏全流程，移动端断线与重复点击验证通过。
- P3 原创视觉：选定 1 套方向、1 个物种、核心动作与首批场景；资源来源清楚，真机性能验收。
- P4 AI 切片：按已确认的方案先完成聊天/记忆与家园动作邀请，再完成旅行叙事并整合；兜底、隐私、删除、预算和安全验收全部通过。
- P5 iOS 内测：Godot 导出原生工程、真机、隐私清单、签名、TestFlight；正式发布另行批准。

暂不承诺日历工期；每阶段评估上一阶段结果再排期。多人社交、开放 UGC、交易、广告、IAP 和运营后台完整权限系统不进入首个闭环。
