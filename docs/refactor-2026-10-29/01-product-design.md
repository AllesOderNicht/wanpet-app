# 丸宠产品设计重构方案

> 本文件为重构方案。2026-10-29 后续实现进度见 [第一轮实现说明](04-implementation.md)，不应把方案中的目标当成已交付功能。
日期：2026-10-29。状态：设计提案，尚未实施。

本方案把丸宠的主线改为：**一只记得你、会自己过日子、能与你一起创造生活环境的 AI 宠物。** 旅行、聊天、生图和收藏，都围绕这只宠物发生。

阅读顺序：[产品与界面](01-product-design.md) → [功能如何连起来](02-functional-design.md) → [代码和制作流程怎么改](03-technical-design.md)。只想先判断方向，阅读本篇即可。

## 1. 用户每天打开丸宠，是为了什么

主要体验是陪伴。用户打开应用，先看到宠物正在做什么，再决定陪它聊聊、照顾它、布置小家，或者只是安静看一会儿。

本稿默认优先做中文 iOS / Android 手机体验；第一版完整体验以一只宠物为主，但每只宠物都有独立身份、画像和记忆。美术延续原创、柔和、手绘的方向。这里的宠物可以说话，也可以看书，但保留动物的动作习惯与自主性。具体名字、世界观、收费方式均不是已确定事项。

三个值得反复回来的理由：

| 用户感受 | 产品必须做到的事 |
| --- | --- |
| “这是我的那一只。” | 外观、性格、习惯和共同经历连续；换衣服、换模型供应商后仍是同一只宠物 |
| “我不操作，它也在生活。” | 饿了吃、困了睡、需要时上厕所，能探索环境，也会选择暂时独处 |
| “我能改变它的生活。” | 新食物、新家具、新房间能实际影响行为，并被记住 |

不靠长时间不登录就生病、死亡或责怪主人制造压力。离开期间宠物可以受到基础照顾；回来时看到少量真实生成的生活摘要。

## 2. 现在有哪些基础，哪些地方断开了

以下是当前本地代码的盘点，不代表线上版本或真机验收结果。

| 能力 | 已有基础 | 距离目标还缺什么 |
| --- | --- | --- |
| 家园与移动 | RN 页面嵌入 Godot，小屋、庭院、寻路、猫动画 | 大部分家具只是背景画；活动范围小，物件不能统一交互 |
| 自主活动 | 吃、睡、观察、嗅闻、休息、靠近、退开；有需求数值与规则兜底 | 排泄、清洁、读书未形成玩法；行为没有统一读取长期记忆 |
| 宠物画像 | 宠物 ID、物种、昵称；生活状态里有三项性格倾向 | 缺少独立、可管理、版本化的完整画像；当前存档仍是一名玩家一只宠物 |
| 聊天 | 文字、看图、动作邀请；有语音输入适配 | 对话与行为的性格表达不完全统一；聊天面板遮住较多生活画面 |
| 记忆 | PostgreSQL 保存条目，mem0 检索；支持查看、纠正、删除 | 自主生活、旅行、道具使用没有统一接入同一套经历与习惯系统 |
| AI 图片 | 聊天生图、改图、赠图、旅行明信片；有任务与预算记录 | 生成结果主要是图片，不能直接变成可使用的宠物、房间或道具 |
| 旅行与收藏 | 出发、消耗、领取、账本、收藏的服务端闭环 | 仍有测试设定；正式自主出发、旅途经历与性格成长未完整串联 |

已有账号、存档、事务、待确认操作、记忆删除和图片任务机制值得保留。重构重点放在连接这些能力，以及替换不适合长期扩展的场景和动作组织方式。

## 3. 用一天的生活说明完整体验

以下“小栗”仅为演示名字。

**早上。** 打开应用，小栗正在窗边醒来。它说：“今天还坐窗边吗？”这句话来自之前一起在窗边读书的记录。没有这条记录时，它不会编造这个回忆。

**吃饭。** 它饿了，会看一眼碗，走过去，调整方向，再低头吃。碗空了，它会提示；用户补粮后，食物库存、碗里的余量、饱腹状态一起变化。

**饭后。** 经过一段游戏时间，它去猫砂盆。猫砂盆变脏，清理后恢复。默认用简洁可爱的表现，不做写实排泄特写。

**下午。** 用户说“给你做一个蓝色的小书架”。应用进入创作流程：先显示设计预览，再检查尺寸与摆放位置。放入房间后，小栗可以靠近、嗅闻；书架里有可读的书且宠物具备相应动作时，才会真正看书。

**晚上。** 用户问“今天过得怎么样”。它能把吃饭、读书和探索的实际经历连起来讲。普通小事不会全部变成永久记忆，反复发生的选择才逐渐形成习惯。

```mermaid
flowchart LR
    A[身体需求与心情] --> B[结合画像和记忆作选择]
    B --> C[在家园或旅途中行动]
    C --> D[实际完成后改变状态]
    D --> E[形成经历和习惯]
    E --> B
    E --> F[聊天能谈起这些事]
    F --> G[主人陪伴或创造新物品]
    G --> C
```

## 4. 首页重做为一个能生活的小家

### 4.1 页面结构

打开后直接进入家园。场景承担主要视觉，界面帮助用户理解宠物和发起互动。

```text
┌──────────────────────────┐
│ 小栗 · 放松，刚睡醒       设置 │
│ 小屋 / 庭院                  │
│                              │
│       可以活动的家园          │
│   食盆   宠物   窝   猫砂盆   │
│                              │
│      “我想去窗边看看。”       │
│                              │
│ 和它说句话…           图片 语音│
│ 照顾       创作       回忆     │
└──────────────────────────┘
```

这是布局草图，文字与状态均为示例，不是最终美术稿。

| 区域 | 放什么 | 点开后做什么 |
| --- | --- | --- |
| 顶部宠物信息 | 名字、当前状态、一个简短心情描述 | 打开画像，看偏好、身体状态和相处变化 |
| 场景 | 宠物和真正可互动的物件 | 点宠物互动；点物件查看用途；点地面发出邀请 |
| 聊天入口 | 一行输入，保留常用图片与语音入口 | 展开短对话面板；需要时进入完整历史 |
| 照顾 | 食物、清理、休息、玩耍 | 显示当前最相关的两三项操作 |
| 创作 | 宠物外观、家具、房间、活动 | 描述需求、查看任务、预览后应用 |
| 回忆 | 日常、聊天记忆、旅途、照片与作品 | 查看来源、修改可编辑记忆、管理私人内容 |

“照顾 / 创作 / 回忆”是轻量工具栏，在家园上展开面板。家具也能作为入口，但不能只靠用户猜哪张画可点。旧版“行囊 / 相册 / 门外”并入对应位置：行囊进入探索准备，相册进入回忆，门负责场景通行和外出。

### 4.2 最重要的交互规则

- **点宠物**：它先有轻微回应，再出现“聊聊、抚摸、看状态”。睡觉时不强制叫醒；反复打扰可能让它想独处。
- **点空地**：显示邀请位置。宠物决定接受、稍后或拒绝；接受后走过去，不瞬移。
- **点食盆**：展示余量和“补一点”。补粮成功后可邀请进食；已经很饱时说明原因。
- **点猫砂盆**：显示干净程度和清理入口。正在使用时等待结束，不突然搬走。
- **长按家具**：进入明确的布置模式。显示可放区域和通道；确认后才保存，取消就恢复。
- **打开聊天**：短对话面板占屏幕约三分之一至二分之一，尽量保留宠物。键盘出现后优先保证输入可用；完整历史可以全屏，并保留“回到家园”。
- **收到动作结果**：文字分别显示“愿意去”“走过去了”“正在吃”“吃好了”。不能在接受邀请时就显示完成。
- **打开普通面板**：宠物继续生活；布置模式暂停受影响的行动。关闭面板后续接，不重播一遍已经完成的动作。

### 4.3 视觉方向

保留水彩、温暖木色和植物，但减少画面里无法参与互动的大型装饰。空间应为宠物活动留位置，食盆、床、厕所也要放得下。

建议把主视角调整为稍俯视的固定镜头。宠物的大小由身体尺寸和镜头共同决定；想看清表情时用近景，避免把宠物单独放大到接近半个屏幕后再用小家具勉强配合。

界面沿用纸白、深棕和低饱和绿，正文使用清楚的系统字体，手写风字体用于标题。状态既有文字也有图标，不只靠颜色。主要触摸区至少 48 个逻辑单位；文字放大、刘海屏、键盘和减少动态效果都要有对应设计。

### 4.4 需要设计的页面与状态

| 页面 | 必须能完成的任务 | 容易遗漏的状态 |
| --- | --- | --- |
| 领养与创建 | 选基础宠物或生成外观，命名，建立画像 | 生成失败仍可用基础宠物进入；未通过检查的造型保留草稿 |
| 家园 | 理解正在做什么，并直接互动 | 宠物外出、资源加载失败、断网、恢复连接 |
| 宠物画像 | 看性格、偏好、身体状态和关系变化 | 新宠物尚无习惯；用户纠正设定；切换宠物 |
| 聊天 | 文字、图片、语音输入，理解动作结果 | 回复慢、停止、动作被打断、图片生成中、记忆服务不可用 |
| 创作工坊 | 提需求、看方案、预览、应用 | 仅生成了图片、暂不支持动作、预算不足、结果待确认 |
| 布置 | 放置、移动、撤销、收纳物品 | 挡住门、无法到达、物品正在使用、保存冲突 |
| 回忆 | 看经历、纠正记忆、收藏图片 | 来源已删除、忘记处理中、旅行插画与实际经历的区别 |
| 探索 | 家附近探索、准备远行、迎接归来 | 没准备好、已经出发、归来待领、领奖结果待确认 |
| 设置与账号 | 登录、安全、声音、动态效果、数据管理 | 登录过期、退出、恢复存档、删除的影响说明 |

## 5. 图层问题应该怎样解决

你的观察对应了真实的结构问题。普通游戏本来就会分层；关键是这些层要遵守同一个空间、尺寸和遮挡规则。

目前有四处明显断点：

1. **背景是一张完整画。** 画里的桌子和前景植物不能分别判断“这部分应该挡住猫”。
2. **物件的前后关系太粗。** 例如猫窝整体位于地面层，不能自然做到“猫在窝里，前沿遮住猫的一小部分”。
3. **猫的不同动作来自不同片段。** 当前已经按动作族校准比例，但素材自身的体形与视角不一致；起身、趴下还被替换成淡入淡出。
4. **只有站立地点，没有身体接触位置。** 代码知道食盆旁在哪里，却没有明确规定嘴要碰到哪里、头朝哪里、爪子站哪里。

增加帧数、继续调图层数字，都不能一次解决这四件事。视频抽帧可以保留为纪念片段、氛围或过渡资源；长期可操作的角色需要更稳定的身体与动作体系。

**建议优先验证：Godot 内统一 3D 空间 + 固定镜头 + 手绘材质。** 看起来仍可像绘本，内部的猫、碗、床却有真实的大小和距离。嘴、脚、家具的位置可以直接对齐。3D 也不会自动做好动画，仍需骨骼、接触位置与制作检查。

正式切换前先做“一只猫、一个房间、一个碗、一个床、一个猫砂盆”的样例。验证走路、吃饭、进窝、上厕所，确认画风和手机性能。若样例不合适，采用规范化的 2D 分层场景与骨骼/手绘动画；业务和记忆设计不受影响。详细比较见[技术方案](03-technical-design.md)。

## 6. AI 创作要交付可用的东西

用户可以自由描述需求，系统需要诚实说明当前能做到哪一步。

| 用户说 | 应交付什么 | 完成的判断 |
| --- | --- | --- |
| “生成一只灰色长毛猫” | 基于已支持身体模板的外观、独立画像、可用动作 | 能走、吃、睡、使用厕所；外观确认后成为新宠物 |
| “把家变成森林小屋” | 新主题、墙地材质、窗外景色和兼容的摆设 | 能走动、物件可达、旧存档保留，预览后再替换 |
| “给它做一个蓝色食盆” | 食盆外观与可进食的能力 | 摆放后能找到它、嘴能对齐、食物余量会变化 |
| “让它看书” | 已支持的读书活动、书本和对应动作 | 找书、就位、阅读、结束，形成一次可追溯经历 |
| “让它驾驶宇宙飞船” | 根据已有能力给出可实现方案或创作草稿 | 没有驾驶玩法时明确只交付插画/摆件，不能假装已经会开 |

新外观和新能力分开管理。长得像书的图片并不会自动成为书，长得像厕所的模型也不会自动拥有如厕功能。完全新的物种、身体结构或复杂动作，需要补齐对应动作和使用规则。

## 7. 分几步完成

| 阶段 | 能交到用户手里的体验 | 推进条件 |
| --- | --- | --- |
| A：解决方向风险 | 场景与动作样例；统一画像和状态定义 | 食盆、床沿、脚底接触过关；确认可接受的画风和设备表现 |
| B：完成生活闭环 | 一只宠物能聊天、记住事情、吃睡排泄、清洁、自由活动 | 行动、数值、画面、记忆一致；断网恢复不重复结算 |
| C：完成创作闭环 | 生成可用食盆、房间主题、同身体模板的新宠物；支持看书活动 | 从描述到实际使用全程可追踪，失败可恢复 |
| D：扩大生活世界 | 自主探索、旅行经历、更多活动和物种、多宠 | 原有存档能迁移；新能力主要通过资源和配置加入 |

B 是最小的完整 AI 宠物体验，C 把自由创造加入主线，D 再扩大内容。每阶段按可玩的结果验收，不能只按增加了多少页面或模型接口验收。

## 8. 怎么判断这次重构成功

先验收以下具体场景：

- 同一只猫连续走路、吃饭、睡觉，身体不忽大忽小，脚不明显滑动，嘴能对准碗。
- 放一个新食盆到另一处，宠物能重新走过去；摆在障碍物里面时无法保存。
- 用户说喜欢窗边，允许保存后，这件事能被聊天和合适的自主选择共同使用；删除后两边都不再使用。
- 实际吃过饭，状态和回忆才改变；被打断、无食物时不会显示“吃好了”。
- 离开一晚再回来，有有限的生活摘要；没有无限模型调用、异常扣粮或重复奖励。
- 一个生成的蓝碗，从创作预览到放进家园再到真正被使用，不需要开发者手工改页面。

上线后再观察：首次完成互动的人数、次日愿意回来的用户、可用生成物占比、动作失败率、记忆纠错率和每个活跃宠物的 AI 成本。先建立基线再定增长目标，避免用“聊得越多、消耗越高”替代陪伴质量。
